# Swarm Simulator in Rust

A port of the Swarm Simulator engine (`engine/src`, TypeScript) to Rust. The
plan, the design decisions and the parity results are in [PLAN.md](PLAN.md).

## Crates

| Crate | Path | What it is |
|---|---|---|
| `swarm-num` | `crates/num` | Big numbers (`f64` mantissa, `i64` exponent), parsing, the game's number formatting (`format_short`, `format_long`). |
| `swarm-data` | `crates/data` | The game data (`data/gamedata.json`, generated by `tables` and committed), resolved into typed ids and tables. |
| `swarm-engine` | `crates/engine` | The game: `State`, `Engine` (queries, `apply(Command)`, `advance`, `load`), offline progress, achievements, statistics, undo. No clocks, files or threads, so it builds for wasm. |
| `swarm-save` | `crates/save` | Save formats: v2 (`SW2|` + lz-string JSON) and the legacy v1 reader (and writer, feature `legacy-write`). |
| `swarm-scenario` | `crates/scenario` | The parity harness: replays the TS engine's scenarios and goldens and compares the results (binary `swarm-scenario`). |
| `swarm-cli` | `crates/cli` | The `swarm` command-line game. |
| `swarm-tui` | `crates/tui` | The `swarm-tui` terminal game (ratatui + crossterm). |

`num`, `data`, `engine` and `save` must stay wasm-portable. A wasm build
for the web app and a Tauri shell are planned (PLAN.md section 7).

## Build and test

```sh
cd rust
cargo build --release -p swarm-cli     # target/release/swarm
cargo build --release -p swarm-tui     # target/release/swarm-tui
cargo test                             # every crate, including the 12 goldens
cargo fmt --check
cargo clippy --all-targets --all-features -- -D warnings
```

## Playing with `swarm`

```sh
swarm new                       # start a game
swarm show                      # units, upgrades, costs; * marks what you can buy
swarm buy drone 10              # also 50%, =12, @1e6, 1.5k, "1.5 billion"
swarm buy-max drone --percent 25%
swarm upgrade hatchery          # or: upgrade-max <name>, upgrade-all
swarm advance 3h                # let game time pass (90s, 2d, 1h30m)
swarm undo                      # again to redo
swarm ascend
swarm respec                    # free respec if you have one, else energy
swarm stats
swarm achievements --all
swarm export [--legacy]         # print the save (v2, or v1 for the TS game)
swarm import save.txt           # v1 or v2, `-` for stdin
swarm convert old.txt new.txt [--to v1|v2]
swarm scenario golden ../engine/test/golden/early-game-1.json
swarm bench
```

`swarm --help` and `swarm <command> --help` describe every option. `show`,
`stats` and `achievements` take `--json`; `--long` prints long number names.

The game runs only while a command runs: time passes between commands as it
does while the browser game is closed. `advance` moves the game clock ahead
of the wall clock.

The save is `$XDG_DATA_HOME/swarm/save.txt` (default
`~/.local/share/swarm/save.txt`), or `--save <path>` / `$SWARM_SAVE`. Every
change rewrites it atomically as a v2 save and keeps the previous one as
`save.prev.txt`; the undo snapshot is `save.undo.txt`. `$SWARM_NOW_MS` fixes
the clock (epoch ms) for reproducible sessions.

Commands that write the save hold `save.lock` (pid and start time) next to
it. While `swarm-tui` (or another `swarm`) holds it they exit 3 naming the
pid; `--force` overrides. A lock whose process is gone is ignored.

Exit codes: 0 ok, 1 refused by a game rule (can't afford, nothing to undo),
2 usage or parse error, 3 I/O error, unreadable save or locked save.

## Playing with `swarm-tui`

```sh
swarm-tui                       # or: swarm-tui --save path/to/save.txt
```

A live game in the terminal (Linux). It uses the same save as `swarm`
(`--save`, `$SWARM_SAVE`, else `$XDG_DATA_HOME/swarm/save.txt`; a missing
save starts a new game), writes it atomically every 30 s and on quit (the
previous one is kept as `save.prev.txt`). It holds `save.lock` for the
whole session, so `swarm` refuses to write the save meanwhile and a second
`swarm-tui` refuses to start; `--force` takes the lock over. SIGTERM, SIGHUP
and SIGINT save and quit cleanly. `save.undo.txt` is shared with `swarm`:
undo works across a hand-off for 30 s.

The game ticks at 10 Hz on the monotonic clock and checks the wall clock
once a second, so after a suspend it catches up the time away and shows
a welcome-back report. `$SWARM_NOW_MS` pins the starting wall clock.

Screens: one tab per unlocked game tab (unit list with counts, rates and
● affordable / ↑ upgrade markers; the selected unit's costs, production,
buy buttons and a count sparkline; its upgrades and abilities with costs,
live effects and buy buttons), then Achievements, Stats and Options. `a`
opens the ascension panel. Panes sit side by side from 100 columns and
stack below that. Tutorial tips show above the status bar; the status bar
shows messages, the undo window and the mouse/animation state.

Keys:

| Key | Does |
|---|---|
| `1-9, 0` | go to tab N (a lone digit waits 0.4 s for a count); Alt-N at once |
| `Tab / Shift-Tab` | next / previous tab |
| `j k, ↓ ↑` | move in the list (with a count: 5j) |
| `g G, Home End` | first / last row |
| `PgDn PgUp, ^D ^U` | page down / up |
| `Enter, l, →` | open the unit's upgrades; on an upgrade, buy one |
| `Esc, h, ←` | back out; close a window |
| `b` | buy 1 of the unit (100b buys 100) |
| `B` | buy the max of the unit |
| `u` | buy 1 level of the selected upgrade (5u buys 5) |
| `U` | buy the max of the selected upgrade |
| `% or i` | type an amount: 1.5k, 25%, =N exactly, @N to have N |
| `a` | ascension panel (y ascends, r respecs) |
| `r` | respec (asks first) |
| `z` | undo the last purchase within 30 s; again to redo |
| `f` | short / long numbers |
| `A` | animation on / off |
| `m` | mouse capture on / off (off: select text with the mouse) |
| `:` | command line |
| `?` | this help |
| `^L` | repaint |
| `q, ^C` | save and quit |

Commands (type `:` first; Tab completes commands, unit and upgrade names):

| Command | Does |
|---|---|
| `:buy <unit> [amount\|max]` | buy units; amount like 100, 1.5k, 25%, =N, @N |
| `:upgrade <name> [amount\|max]` | buy upgrade or ability levels |
| `:ascend` | ascend now |
| `:respec` | respec (free if you have one) |
| `:undo` | undo / redo |
| `:export [file]` | write the save (v2) to a file, or show it |
| `:import <file>` | load a v1 or v2 save |
| `:anim on\|off` | animation |
| `:mouse on\|off` | mouse capture |
| `:long \| short` | number format |
| `:tab <name\|N>` | go to a tab |
| `:save` | save now (also every 30 s and on quit) |
| `:quit` | save and quit |
| `:help` | this help |

Amounts go through the game's number parser: `100`, `1.5k`, `1.5 billion`,
`25%` (of what you can afford), `=N` (exactly N units, ignoring twins),
`@N` (enough to have N).

Mouse: click tabs, units, upgrades and `[buttons]`; the wheel scrolls the
list under it; double-click a unit to open its upgrades. Mouse capture
(`m`, `:mouse off`) stops the terminal's own text selection, so turn it
off to copy text (e.g. `:export`); many terminals also select with
Shift-drag while it is on. Animation (`A`, `:anim`), mouse capture and the
number format are saved in the save's options bag (`tui.anim`,
`tui.mouse`, `tui.numformat`).

## Desktop (Tauri)

`crates/tauri` (`swarm-tauri`) wraps the built web app (`app/dist`) in a
Tauri 2 window. The engine runs as wasm inside the webview, so the desktop
game is the web game; there is no second code path. Linux only.

It is left out of the workspace's `default-members`, so `cargo build`,
`cargo test` and `cargo clippy` in `rust/` don't need the GTK libraries.
Name it to build it (`cargo build -p swarm-tauri`).

System packages (Ubuntu 24.04):

```sh
sudo apt-get install libwebkit2gtk-4.1-dev libayatana-appindicator3-dev \
  librsvg2-dev libxdo-dev libssl-dev build-essential file patchelf pkg-config
```

Plus Rust stable with `rustup target add wasm32-unknown-unknown`, the
wasm-bindgen CLI at the version in `Cargo.lock`
(`cargo install wasm-bindgen-cli --locked --version 0.2.130`), Node 22 with
pnpm (`pnpm install` at the repo root), and the Tauri CLI:

```sh
cargo install tauri-cli --locked --version '^2'
cd rust/crates/tauri
cargo tauri dev       # run against a fresh app build
cargo tauri build     # AppImage and .deb
```

`cargo tauri build` first runs `beforeBuildCommand` from the repo root:
`SWARM_WASM_REQUIRED=1 pnpm --filter "@swarmsim/app..." build`, i.e. the app
and its workspace dependencies, failing if the wasm engine can't be built.
It then compiles the `swarm-desktop` binary and bundles it with `app/dist`
into `rust/target/release/bundle/appimage/Swarm Simulator_<version>_amd64.AppImage`
and `rust/target/release/bundle/deb/Swarm Simulator_<version>_amd64.deb`. The
AppImage carries its own WebKitGTK; the .deb depends on the system's
`libwebkit2gtk-4.1-0`. The icons in `crates/tauri/icons` were generated
from `app/public/icons/icon-512.png` with
`cargo tauri icon ../../../app/public/icons/icon-512.png`.

Saves: the shell exposes `load_save` and `store_save` commands that keep the
save in `$XDG_DATA_HOME/com.swarmsim.desktop/save.txt` (default
`~/.local/share/com.swarmsim.desktop/save.txt`), written atomically with the
previous save kept as `save.prev.txt`. The app uses them instead of
localStorage when `window.__TAURI__` exists; `crates/tauri/shim/storage.ts`
shows how. The fs plugin is enabled with its scope limited to that directory.

CI: `.github/workflows/desktop.yml` runs on `v*` tags and by hand on
Ubuntu 24.04. It builds the AppImage and .deb plus stripped `swarm` and
`swarm-tui` binaries, uploads them as a workflow artifact and, on tags,
attaches them to the GitHub release.
